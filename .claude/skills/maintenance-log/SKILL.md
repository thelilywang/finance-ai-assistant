# 撰寫維護日誌

`docs/MAINTENANCE_LOG.md` 記錄技術債、優化候選與決策依據。重點不只在「做了什麼」，
更在「為什麼這樣取捨」與「什麼是已知但刻意延後的」。

**讀者是面試官與其他外部人士**，沒有本專案的脈絡，也沒有耐心讀過程。
每個結論要能獨立成立，專有名詞首次出現時補一句說明。**篇幅與工程量成比例**：
裝一個套件、接一個服務就是短短一章，不要因為過程曲折就寫長——過程屬於對話，不屬於檔案。

## 文件骨架

上方是固定索引，依序五節，其後為日期章節（新的往下加，`---` 分隔）：

```
## 專案狀態
## 待辦
## 已知限制
## 後續方向
## 已評估不採用      ← 表格：| 項目 | 結論 | 觸發條件 | 詳見 |
## YYYY-MM-DD　<當日主題>
```

## 索引撰寫規則

索引（上方五節）**每項最多兩行**：只寫現況結論＋「詳見 YYYY-MM-DD 章節（第N節）」。
演變過程——下修、上移、推翻、回答了哪個未決問題——寫進日期章節，不寫在索引。

- 新增或撤下一項，索引只改一兩行；論證寫進當天的日期章節。
- 從索引刪除任何內容前，先確認日期章節已有同樣資訊；沒有就先搬過去再刪。
- 「已評估不採用」固定四欄：項目｜結論｜觸發條件（什麼情況下要重新評估，無則填 `—`）｜詳見。

## 不入檔的內容

適合在對話裡跟使用者說明，不要寫進日誌：

- **需求文件本身的錯誤或不一致**——屬於往返，不是專案決策。
- **第三方或自架基礎設施的故障狀態**——與本專案程式無關。
- **驗收過程的曲折**（查錯端點、誤判、死路）——驗收段只留結果與數字。
- **內部實作細節**——需要時降進改動內容表；也不記開發工具設定（`.claude/` 下的
  skill、subagent、hook），這類改動留在 commit message 即可。

> 實例：Langfuse 串接初稿 1,982 字含故障與曲折，砍成 1,060 字後只剩掛載點、
> 失敗處理方式、環境限制與驗收數字。

**例外：有實測數據、或被索引引用的章節壓縮幅度要小**——砍掉數字會讓「詳見」
指向不存在的內容。壓縮後 `grep` 每個被刪的數字，確認沒有別處還在引用。

## 日期章節

**標題只寫主題，不列舉當天做的每件事**（不要寫成並列名詞短語堆砌當天項目）。
細項放 `###` 小節，單一主題不分節。

開頭一段話交代當日主軸與各項之間的關聯，是章節的黏著劑，不要省略：

> 同一條調查線：先修好 X 的退化，再回頭評估 Y 與 Z 兩個方向，後兩者實測後皆不採用。

章節末固定一張 `### 改動內容` 表格，三欄 `| 項目 | 改動說明 | commit |`。
commit 欄填短 hash，**從 `git log` 取得，不得憑印象填寫**；沒有單一對應 commit
（尚未 commit、實測後回退、多 commit 混合）填 `—`，不要編造。散文裡引用的 hash
同樣要查，不是只查 commit 欄。

**一天只有一個 `##` 日期章節**：`grep "^## <日期>"` 確認全檔該日只有一個。
當天多做幾件事，收進同一章的不同 `###` 小節，不新起一章。
續寫已存在的章節是往裡加；已寫成兩章的（同日，或先做 X 再改做 Y）要合併，
且是拆掉「兩章」這個結構本身：開頭改寫成交代整條線，後章「上一節如何」的指涉
一併改寫；若其實是兩件獨立的工作，原標題降為兩個 `###` 子節，只在 `##` 層級合併，
判準是**後章是否承接前章的結果**。兩張改動內容表合併成一張，commit 欄逐列保留原值。
合併或改寫後 `grep` 舊標題文字，確認檔內外沒有還指著它的互引。

## 敘事慣例

- **散文優先於條列**：有因果關係的判斷連寫成段落；條列只用在彼此無關的並列事項。
- **結論先行，且只講一次**：評估類小節以 `**結論：...**` 開頭，再展開依據，
  結尾不重述。
- **數據具名**：量測結果進表格並附量測條件（同容器、`temperature=0`、每情境三次），
  沒實測過的不寫數字；表格之後只寫表格看不出來的事，不把數字再條列一次。
- **推翻的假設要留下**：寫明原假設、實測結果如何相反、真正的原因——這是唯一該保留的
  「過程」，與驗收曲折不同：前者是技術判斷，後者是查錯地方。
  > 「Apple 原生框架應該更快」是合理但錯誤的直覺：失敗源於容量而非框架。
- **取捨標明代價**：用 `**取捨**：` 寫換來什麼、代價是什麼，兩邊都要寫。
- **引用程式碼寫函式名**（`src/graph.py` 的 `generate`），少用會隨改動失效的行號。
- **用詞**：production 譯「正式環境」，不用「生產環境」。
- **已知限制不隱藏**：用 `**已知限制**：` 收成一兩句，不逐項盤點未變動的檔案。
- **同一事實只在一處講**：論證、數字、推翻過程一律放日期章節；索引只放一句結論＋詳見，
  不複製章節內容。
- **決策可追溯**：跨章節用「詳見 YYYY-MM-DD 章節（第N節）」互引。已失效的舊敘述用引言 `>`
  保留並註明何時被取代，不要刪除；被取代者與取代者整併成同一章時，該引言要改寫進散文
  （指向自己就是死鏈）。

## 索引各節的寫法

格式一律是 **粗體標題**（必要時附函式名）——一句結論——詳見，不超過兩行。

- **待辦**：只放現在要做的事，依 CP 值排序編號。卡住的項目寫**卡在哪**，而不是怎麼做。
- **已知限制**：寫限制本身，以及目前靠什麼兜住。
- **後續方向**：寫前置條件，也就是要先有什麼才能動工。
- **已評估不採用**：結論要附觸發條件。

進度更新、撤下理由、重新排序，一律寫進當天的日期章節；索引只改結論那一句。

## 落筆前檢查

- 先問：這段對不認識本專案的外部讀者有用嗎？往返、他人系統故障、查錯過程一律不入檔。
- 落筆的日期是否已有 `##` 章節？有就寫進去。
- commit hash 來自 `git log`，不是憑印象；未 commit 就填 `—`。
- 每個數字有對應實測與量測條件；每個「不採用」都附理由與觸發條件。
- 壓縮後 `grep` 被刪的數字與舊標題，確認索引與其他文件的互引沒有指向不存在的內容。
