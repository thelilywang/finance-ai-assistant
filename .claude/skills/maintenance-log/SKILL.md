# 撰寫維護日誌

`docs/MAINTENANCE_LOG.md` 記錄技術債、優化候選與決策依據。重點不只在「做了什麼」，
更在「為什麼這樣取捨」與「什麼是已知但刻意延後的」。

**讀者是面試官與其他外部人士**，沒有本專案的脈絡，也沒有耐心讀過程。
每個結論要能獨立成立，專有名詞首次出現時補一句說明。

## 只維護重點

**篇幅與工程量成比例。** 裝一個套件、接一個服務，就是短短一章；
不要因為過程曲折就寫長——過程的曲折屬於對話，不屬於檔案。

以下四類**不要寫進日誌**（適合在對話裡跟使用者說明）：

- **需求文件本身的錯誤或不一致**（版本對應寫錯、環境變數兩種寫法）——屬於往返，不是專案決策。
- **第三方或自架基礎設施的故障狀態**（服務的佇列卡住、DB 當掉、快取行為異常）——與本專案程式無關。
- **驗收過程的曲折**（查錯端點、誤判、中途走過的死路）——驗收段只留結果與數字。
- **內部實作細節**（單例旗標、容錯取值怎麼寫、為何放 `finally`）——需要時降進改動內容表。

保留的是：**這東西是什麼、掛在哪、關鍵限制、驗收結果數字**。

> 實例：Langfuse 串接初稿 1,982 字，含 SDK 版本比對、events_only 驗收曲折、
> 自架服務的 Redis 故障、內部實作細節；砍成 1,060 字後只剩「掛載點只有一處」
> 「追蹤失敗不影響問答」「容器內不能用 localhost」與驗收數字。

**例外：有實測數據、或被常設區塊引用的章節壓縮幅度要小。**
砍掉數字會讓「量測數字見 YYYY-MM-DD 章節」指向不存在的內容，比冗長更糟。
壓縮後 `grep` 每個被刪的數字，確認沒有別處還在引用。
（實例：09-13 有實測表且被「保持現狀」兩處引用，只減 15%；
同日無數據的抓取路徑章節減 50%。）

## 文件骨架

兩個常設區塊在前，其後為日期章節（新的往下加，`---` 分隔）：

```
## 目前待辦（依 CP 值排序）
## 保持現狀（已評估，判斷暫不處理）
## YYYY-MM-DD　<當日主題>
```

## 章節整併

**一天只有一個 `##` 日期章節。** 同日不得出現第二個 `##`——當天做了幾件事，
都收進同一個日期章節，主題寫成並列的名詞短語（「抓取路徑紀錄修正與自架 Langfuse 追蹤」）。
章節內部照「日期章節」一節的慣例，該用 `###` 分節就用，這條限制只在 `##` 層級。

續寫當天已存在的章節時，是往該章節裡加，不是新起一章；
已經寫成兩章的（同日、或先做 X 再改做 Y 的前後兩章）合併成一章。
**合併不是把兩章接起來，要拆掉「兩章」這個結構本身**：

- 開頭一段改為交代整條線（「先接上追蹤 → 發現記錄層級不對 → 改逐節點包裝」），
  取代原本各自的開頭；後章的「上一節如何如何」全部失去指涉，一併改寫。
- **拆掉的是「兩章」的結構，不是兩件事的區隔。** 兩章若是同一條線的前後接續，
  併成單一敘事；若其實是兩件獨立的工作（只是同日、同一個大方向），
  原標題降為兩個 `###` 子節，只有 `##` 層級合併。
  判準是**後章是否承接前章的結果**——不承接就別壓成一段，讀者會失去「這是兩件事」的線索。
- 跨章引言 `>` 依「決策可追溯」一條的例外處理。
- 兩張改動內容表合併成一張，**commit 欄逐列保留原值**，不要因為同章就統一填同一個 hash。
  同一檔案在前後兩章各有一列時可併列，commit 欄寫 `—／<hash>`。
- 合併後 `grep` 舊標題文字，確認檔內與其他文件都沒有還指著它的互引。

## 日期章節

標題用全形空格分隔日期與主題，主題為並列的名詞短語。

開頭一段話交代當日主軸與各項之間的關聯——這是章節的黏著劑，不要省略：

> 同一條調查線：先修好 X 的退化，再回頭評估 Y 與 Z 兩個方向，後兩者實測後皆不採用。

單一主題不分節；內容多時才用 `###`。章節末固定一張 `### 改動內容` 表格。

## 改動內容表格

三欄：`| 項目 | 改動說明 | commit |`。
純修復用「修復內容」，跨多檔時用「涉及檔案與函式」。

commit 欄填短 hash，**從 `git log` 取得，不得憑印象填寫**。
沒有單一對應 commit（尚未 commit、實測後回退、多 commit 混合）填 `—`，不要編造。

改動說明欄收檔案與函式名，以及**散文放不下的選型理由**（為何不用某套件、為何選這個 handler）。
表格佔行不佔閱讀負擔，是散文超標時理由的去處。

## 敘事慣例

- **散文優先於條列**：有因果關係的判斷連寫成段落，不要一個決策一行 bullet。
  條列只用在彼此無關的並列事項。

- **結論先行，且只講一次**：評估類小節以 `**結論：...**` 開頭，再展開依據。
  開頭講過就不要在結尾重述——同一個判斷寫三遍是篇幅膨脹最常見的來源。

- **數據具名**：量測結果一律進表格，並附量測條件（同容器、`temperature=0`、每情境三次）。
  沒實測過的不寫數字。表格之後只寫「表格看不出來的事」——為何是這個數字、離散度、拆分貢獻；
  把表格裡的數字再條列一次是膨脹而非說明。

- **推翻的假設要留下**：寫明原假設、實測結果如何相反、真正的原因。
  被推翻的假設比成功的修復更有閱讀價值——它讓讀者不必重走一次死路。
  這是**唯一該保留的「過程」**，與上面要砍掉的驗收曲折不同：
  前者是專案的技術判斷，後者是我當時查錯地方。
  > 「Apple 原生框架應該更快」是合理但錯誤的直覺：失敗源於容量而非框架。

- **取捨標明代價**：用 `**取捨**：` 寫換來什麼、代價是什麼，兩邊都要寫。

- **已知限制不隱藏**：用 `**已知限制**：` 明示這次沒解決的部分。
  收成一兩句，不要逐項盤點未變動的檔案。

- **同一事實只在一處講**：與「保持現狀」重複時**刪章節那份、保留常設那份**，
  章節內以模糊說法帶過（「配額均維持不變」）即可。
  但**刪的是結論不是推導**——常設區塊存判斷結果，日期章節存當時怎麼想錯的。

- **決策可追溯**：跨章節用「詳見 YYYY-MM-DD 章節」互引。
  已失效的舊敘述用引言 `>` 保留並註明何時被取代，不要刪除。
  **例外：被取代者與取代者整併成同一章時，該引言要改寫進散文。**
  引言的作用是指向另一章，合併後它指向自己，留著就是死鏈。
  刪的是「指向」這個形式，不是內容——原假設、實測如何相反、真正原因仍須留在文中。

## 待辦項目

依 CP 值排序的編號列表。每項為 **粗體標題** ＋（`檔案:行號` 或模組的函式名），
內文交代四件事各一兩句：現況如何／為何還沒做／預期做法／影響面。難度或影響面要明寫。

「預期做法」不要寫成設計文件——真要做時會重新設計，寫在待辦裡的設計稿不會被照著執行。
卡住的項目改寫**卡在哪**（「卡在資料來源：既有 API 都沒有該欄位」），比寫怎麼做有用。

持續性項目明確標注，並寫出**可以開始行動的門檻**（「累積約 30 筆以上再分析」）——
沒有門檻的持續項目會永遠停在原地。進度更新以日期開頭追加在原項目下，不改寫原文。

## 保持現狀

每項為 **粗體標題＋判斷結論**（「評估後不採用」「量測後判斷不需處理」「維持觀察」）＋（檔案位置）。
必寫「原本的假設是什麼、為何不成立」——這個區塊的目的就是讓同一件事不被重複評估。
從待辦撤下的項目，寫明何時、依據什麼撤下。

**「不採用」寫在哪一區**：判斷若是元件級、跨日期仍成立（換掉某套件、改用某架構），
寫進「保持現狀」；只有在該次改動脈絡下才讀得懂的才留在日期章節，並留一行指向此區。

**此區存判斷結果，不存推導過程。** 推導屬於日期章節。一項寫到 500 字以上、
開始複述量測過程，就是把章節的職責搬了進來。
新增一項時順手看此區是否已超過最長的日期章節，超過就挑最長的兩三項壓。

## 落筆前檢查

- 先問：**這段對不認識本專案的外部讀者有用嗎**？往返、他人系統的故障、查錯的過程一律不入檔。
- 落筆的日期是否已有 `##` 章節？有就寫進去，不要新起一章——`grep "^## <日期>"` 確認全檔該日只有一個。
- 篇幅與工程量成比例——單一套件串接不需要長篇章節。
- commit hash 來自 `git log`，不是憑印象；未 commit 就填 `—`。
  **散文裡引用的 hash 同樣要查**（「`build_graph()` 於 `ef76670` 改為 async」），
  不是只查 commit 欄——順手用 `git log --oneline -1 <hash>` 確認 subject 與敘述相符。
- 每個數字都有對應的實測與量測條件；每個「不採用」都附理由。
- 壓縮後 `grep` 被刪的數字，確認常設區塊的互引沒有指向不存在的內容。
- 壓縮只刪重述與過程，事後核對決策、取捨、被推翻的假設與實測數字都還在。
