# 撰寫維護日誌

`docs/MAINTENANCE_LOG.md` 記錄技術債、優化候選與決策依據。重點不只在「做了什麼」，
更在「為什麼這樣取捨」與「什麼是已知但刻意延後的」。

**讀者是不熟悉本專案的外部人士**，沒有當時的脈絡。因此每個結論都要能獨立成立：
看得到判斷依據，不必回頭翻程式或問人。專有名詞首次出現時補一句說明。

## 文件骨架

兩個常設區塊在前，其後為日期章節（新的往下加，`---` 分隔）：

```
## 目前待辦（依 CP 值排序）
## 保持現狀（已評估，判斷暫不處理）
## YYYY-MM-DD　<當日主題>
```

## 日期章節

標題用全形空格分隔日期與主題，主題為並列的名詞短語（如「補資料決策失效修復、推理顯示與模型替換評估」）。

開頭一段話交代當日主軸，以及各項之間的關聯——這是章節的黏著劑，不要省略：

> 同一條調查線：先修好 X 的退化，再回頭評估 Y 與 Z 兩個方向，後兩者實測後皆不採用。

內容多時用 `###`／`#### 一、二、三` 分節；單一主題則不分節。章節末固定一張 `### 改動內容` 表格。

**篇幅參考**：既有章節落在 9-71 行，資訊量最大的一章（多個子節、數張量測表、數個被推翻的假設）為 71 行。
明顯超出這個範圍，通常不是內容太多而是密度太低——先照下節的散文慣例壓縮，不要靠刪決策來縮短。

**判斷「是否過長」要用散文字數，不是行數或總字數**：表格佔行不佔閱讀負擔，
一章可能行數較少卻散文更多，讀起來反而更冗。與既有章節比較時算不含表格列的字數
（`grep -v '^|' | tr -d '[:space:]' | wc -m`），09-09 的 2,942 字可作為上限參考。

但**這個字數是「涵蓋那麼多事」才配得上的預算，不是每章通用的及格線**。
09-09 用 2,942 字寫了三個延遲方向、新聞時效、對話持久化與三個財報靜默錯誤；
只寫三件事的一章若也逼近這個數字，就是密度不足而非剛好。
先數這章涵蓋幾件事，再看字數配不配得上——詳見「落筆前檢查」的密度條目。

## 改動內容表格

三欄：`| 項目 | 改動說明 | commit |`。
純修復用「修復內容」，跨多檔時用「涉及檔案與函式」。

commit 欄填短 hash，**從 `git log` 取得，不得憑印象填寫**。
沒有單一對應 commit 時（實測後回退、多 commit 混合）填 `—`，不要留空或編造。

改動說明欄不限於檔名與函式名，**也可以收散文放不下的選型理由**
（為何不用某套件、為何選這個 handler、欄位為何這樣命名）。
散文超標而又不想刪決策時，這裡是理由的去處——見「落筆前檢查」的降級條目。

## 敘事慣例

這節是本文件最有辨識度的部分，也是外部讀者真正在讀的東西。

- **散文優先於條列**：有因果關係的判斷連寫成段落，不要一個決策一行 bullet。
  條列只用在彼此無關的並列事項。同樣的內容——原假設、推翻、替代方案、邊界條件——
  散文能壓進一兩句，拆成 bullet 會膨脹三倍且讀不出先後關係。
  > 原想讀 `items` 與 `primaryDocDescription` 辨識性質，取樣後推翻——兩欄位對 6-K 全為空。
  > 改採 `reportDate`：財報的報導期末與申報日不同，公告類則填當天；再加「月份需為 3/6/9/12」⋯⋯

- **結論先行，且只講一次**：評估類小節以 `**結論：...**` 開頭，再展開依據。
  結論出現在小節開頭就不要在結尾重述，依據講完也不要再總結一次——
  同一個判斷寫三遍是篇幅膨脹最常見的來源。
  > **結論：功能可行但不納入，開啟推理讓單題延遲增為 6.7 倍。**

- **數據具名**：量測結果一律進表格，並附量測條件（同容器、`temperature=0`、每情境三次、
  序列執行避免互搶資源）。沒實測過的不寫數字。
  表格之後只寫「表格看不出來的事」——拆分貢獻、離散度、為何是這個數字；
  把表格裡的數字再條列一次，是篇幅膨脹而非說明。

- **同一事實只在一處講**：前一條管的是小節內，這條管的是跨小節。同一個事實在兩個小節
  各自都「講得通」時最難發現——寫的時候各自合理，連讀才看出是同一句話說了兩遍。
  常見三型：**量測性質重複**（離散度在實測小節與結論小節各講一次）、
  **背景事實重複**（「以本地模型生成為瓶頸」既用來說明為何需要 logging，
  又用來說明為何省下的毫秒不重要）、**前向引用數字**（取捨段寫「下方實測省約 212 ms」，
  而表格與說明馬上就會給出同一個數字）。
  處理方式是留資訊量最大的那一處，其餘刪成指涉或直接拿掉，**不要改寫成同義句**。
  這類冗餘是詞語層級不是結構層級，刪完行數往往不變、字數才降——
  行數沒少不代表沒效果。

- **推翻的假設要留下**：寫明原假設、實測結果如何相反、以及真正的原因。
  被推翻的假設比成功的修復更有閱讀價值——它讓讀者不必重走一次死路。
  > 「Apple 原生框架應該更快」是合理但錯誤的直覺：失敗源於容量而非框架。

- **取捨標明代價**：用 `**取捨**：` 寫換來什麼、代價是什麼，兩邊都要寫。

- **已知限制不隱藏**：用 `**已知限制**：`／`**未變動範圍**：` 明示這次沒解決的部分，
  以及這個修復「不等於」解決了什麼。

- **決策可追溯**：跨章節的決策演變用「詳見 YYYY-MM-DD 章節」互引。
  已失效的舊敘述用引言 `>` 保留並註明何時被取代，**不要刪除**——
  當時的判斷本身就是紀錄的一部分。

## 待辦項目

依 CP 值排序的編號列表。每項為 **粗體標題** ＋（`檔案:行號` 或 `模組` 的函式名），
內文交代四件事：現況如何／為何還沒做／預期做法／影響面。

難度或影響面要明寫：「難度：小（0.5-1 天）」「影響面較大，刻意留待下一階段獨立處理」。

持續性項目（不是做完就關掉的）明確標注，並寫出**可以開始行動的門檻**，
例如「累積約 30 筆以上再分析」——沒有門檻的持續項目會永遠停在原地。

進度更新以日期開頭追加在原項目下，不改寫原文：

> **2026-09-13 首次嘗試分析：資料量不足，未能得出結論。** ……

## 保持現狀

**「不採用」寫在哪一區**：判斷若是元件級、跨日期仍然成立（換掉某個套件、改用某種架構），
寫進「保持現狀」並註明何時依據什麼判斷；只有在該次改動脈絡下才讀得懂的（是當日三個方向之一、
抽出來就失去前因），才留在日期章節內。章節內留一行指向「保持現狀」即可，不要兩邊各寫一份。

每項為 **粗體標題＋判斷結論**（「評估後不採用」「量測後判斷不需處理」「維持觀察」）＋（檔案位置）。

必寫「原本的假設是什麼、為何不成立」。這個區塊的目的就是讓同一件事不被重複評估，
只寫「不做」而不寫理由的話，下次還是得從頭評一遍。

從待辦撤下的項目，寫明何時、依據什麼撤下。

## 落筆前檢查

- commit hash 來自 `git log`，不是憑印象。
- 每個數字都有對應的實測與量測條件。
- 每個「不採用」都附理由，讀者不必重新評估。
- 不預設讀者知道本專案脈絡。
- 全文不出現讀者身分或場合的具體舉例字詞。
- 整章連讀一遍找重複句：同一事實是否在兩個小節各講一次、是否前向引用了下文的數字。
- 壓縮只刪重述與贅詞，事後核對決策、取捨、被推翻的假設與實測數字都還在。
- **密度不足時依序處理，不要跳級**：①找重複句 → ②檢查 `###` 結構 → ③壓散文贅詞
  → ④選型理由降進表格。前一級沒做完不要動下一級，因為後面的代價一級比一級高
  （①②不損失任何東西，③會動到語氣，④會讓散文失去論證）。以下四條依此順序。
- **密度要對內容量算，不是對別章的字數算**：散文字數只是分子，分母是這章實際涵蓋多少事
  （幾個獨立主題、幾個子節、幾組實測、幾個被推翻的假設）。
  「字數低於既有章節」不等於夠密——涵蓋範圍小的一章，字數本來就該明顯更低。
  比較時先數分母再看分子：主題數少一半、字數卻只少一成，就是密度不足，該壓。
  （實例：09-13 三個主題 2,750 字，09-09 涵蓋近三倍的事才 2,939 字——09-13 仍偏鬆，
  壓到 2,430 字。若只比絕對字數會誤判成「已經夠短」。）
- **密度不足時先看結構，再看字**：`###` 數量會被讀成「這章涵蓋幾件事」，
  把某個發現獨立成小節，等於把分母灌大、密度變差。
  檢查每個 `###` 是不是真的獨立主題——若它其實是前一節的一個發現（實測的結論、某個容量判斷），
  降級成段落並以粗體起頭，比刪字有效且不損失任何內容。
  同理，只有一兩句的小節通常該併進相鄰段落。
  （實例：09-13 的「連線池容量」是實測的發現、「保留循序路徑的理由」與實測結論重複，
  兩個 `###` 降級併入後，5 節 → 4 節、58 → 50 行。）
- **「決策不難」與「決策可刪」是兩件事**：容易的決策（選標準庫、選某個 handler）仍要留下選型理由，
  可壓縮的是它周圍的散文——把鋪陳、機制解釋與理由合併成一句，而不是拿掉理由本身。
- **散文壓到底仍超標時，把選型理由降進改動內容表**：理由不刪、換一個欄位放。
  判準是「這句非得在散文裡讀到嗎」——散文留**為何要做**（問題、風險）、**約束**（隱私、合規）
  與**實測數字**；純設定選擇（用哪個 handler、為何不用某套件、欄位怎麼命名）移進表格的改動說明欄，
  散文以「（設定細節見改動內容表）」帶過。
  **代價要知道**：那節會從「有論證」變成「有指引」，讀者得跳到表格才看得到為什麼。
  一節裡若連「為何要做」都得搬走，就是搬過頭了。
  （實例：09-13 logging 節 1,004 字／佔全章 41%，散文已無贅詞，
  將 structlog 選型、Timed vs Rotating、欄位命名降進表格後為 431 字／23%。）
