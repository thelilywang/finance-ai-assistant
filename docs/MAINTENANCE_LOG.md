## 2026-09-03　LLM 與資料層穩定性修復　`LangGraph` `資料層`

> 本節提及的 `route_after_retrieve`／`auto_fetch` 已於 2026-09-07 改造時移除，內容保留作為當時的決策紀錄。

三項修復：

- **LLM 重試**：`llm` 加上 `.with_retry(stop_after_attempt=3)`，Ollama 冷啟動或短暫逾時時重試，不再直接中斷整個 graph 節點。
- **連線池**：`get_connection()` 改用 `psycopg_pool.ConnectionPool`，不再每次新開 TCP 與 PG 認證。預設 `timeout=30` 秒遠慢於原本毫秒級失敗，改成 `timeout=2` 後測試由 32 秒降到 4-5 秒——正常連線本該是毫秒級，2 秒內連不上即代表 DB 已掛。
- **Ticker 誤判治本**：regex fallback 會把純英文問題裡的一般單字當 ticker；改為 `extract_filters` 用 `with_structured_output(ExtractedFilters)`，代號由 `normalize_ticker()` 正規化並驗證，regex fallback 直接移除（多標的問題當時改為回報錯誤，該降級已於 2026-09-16 由多標的支援取代）。三處 `isdigit() and len==4` 的台股判斷會把 ETF 6 碼、特別股與可轉債字母尾碼誤判成美股，統一改用 `is_tw_ticker()`。

## 2026-09-04　靜默選錯修正　`資料層` `LangGraph`

兩項各自獨立、皆屬「靜默選錯」而非報錯的準確度缺陷。

### 一、MOPS 固定選到英文版財報

評估 MOPS 爬蟲改用 Playwright 時，**結論不採用**：端點是純表單 POST，換工具不提升穩定性；觸發條件為 MOPS 移除直連表單端點。評估時向端點送真實請求（2330，115 年），發現同一季度同時列出 `_AI1.pdf`（中文主文）與 `_AIA.pdf`（英文版），而 `sorted(files)[-1]` 依字典序（`'AIA' > 'AI1'`）每次固定選到英文版，是系統性錯誤，也與中文財經助理的定位不符。修法是先篩最新月份、優先選 `_AI1.pdf`，選到非中文主文時告警而非靜默降級。**未變動範圍**：爬蟲本體仍依賴頁面結構，改版仍會失效。

### 二、Rewrite regex bypass 誤判追問

`rewrite_question` 原本在出現 4 位數字或 2-5 碼大寫字母時視為已指名代號、跳過改寫，會誤判仍依賴上下文的追問：「2024 年的營收呢？」被當成台股代號，「ROE 表現如何？」被當成美股 ticker（真實 Ollama 驗證確認）。拿掉 bypass，有歷史時一律交 LLM 改寫（prompt 已寫明「問題已獨立完整就原樣輸出」）。**取捨**：每輪有歷史的對話固定多跑一次 LLM。

## 2026-09-07　MCP tool-calling 架構改造：補資料決策交給 LLM　`LangGraph`

### 背景與取捨

補資料的決策原本寫死在程式裡（`needs_refetch()` 的日期門檻）：只認「新聞日期距今幾天」單一維度，無法理解「問法暗示需要多新的資料」；對外的 MCP tool 又是門面式的，外部 client 拿不到中間決策點。改造把決策權交給 LLM，讓 Chainlit 內部的 LangGraph agent 與外部 client（如 Claude Desktop）走相同協定、共用同一份 tool 定義。**取捨**：換來判斷能涵蓋規則寫不出的情境，以及外部 client 能自行決定要不要補抓；代價是每題多一次 LLM 往返、判斷正確性不再有程式保證——改造當下即列為主要風險，實際也確實發生。

### 架構與改動

```
rewrite_question → extract_filters → agent ⇄ tools → assemble → (generate | no_result)
```

三個單一職責 tool 取代原本兩個門面式 tool：`search_knowledge_base`（只檢索）、`fetch_company_data`（只抓指定公司財報與新聞）、`fetch_market_overview`（只抓市場總覽）；「要不要看大盤脈絡」屬語意判斷，故後兩者分開，台美來源分派屬格式規則則留在 tool 內。`agent` 與 `tools` 往返直到 LLM 不再要求工具（上限 4 輪，避免反覆抓外部網站），`assemble` 還原既有欄位，下游與前端不受影響。MCP server 由 stdio 改為 HTTP transport 並加 Bearer token 驗證——SDK 內建 `AuthSettings` 是完整 OAuth，對單一共享密鑰過重，改用最小 middleware，未帶或不符回 401。

導入時另遇兩個套件層面問題：容器以 service 名稱連線被 DNS rebinding 防護擋成 421，改以 `MCP_ALLOWED_HOSTS` 設定允許清單而非關閉防護；`langchain-mcp-adapters` 回傳的 `ToolMessage.content` 是 content block 陣列而非字串，新增 `_tool_text()` 兩種格式都支援。

端到端測試發現資料過期時未觸發補抓，是相對於改造前確定性規則的功能退化。當下判斷為「模型指令遵從能力不足」，後續盤查證實有誤，真正根因與修復見 2026-09-08 章節。

## 2026-09-08　改造後的退化收斂與模型方向評估　`LangGraph`

同一條調查線：先修好 09-07 改造留下的退化，再回頭評估「開啟推理」與「換更快模型」兩個方向，後兩者實測後皆不採用。

### 一、補資料決策失效（根因修復）

**問題**：資料停在兩個月前仍直接作答，改造前的確定性規則必定會補抓。**根因**：初判為指令遵從能力不足，但模型其實已算出天數、得出「需要補抓」，只是寫成文字而非結構化 tool call；A／B 對照確認是 `reasoning=False` 連帶壓掉了 tool-calling 能力。**修法**：依用途拆成兩個模型實例，`agent` 節點改用不關推理的 `_tool_llm`（輸出不進使用者可見的串流），其餘節點沿用 `_base_llm`。排查時另修四項同源缺陷：prompt 從未提供當日日期（改為預先算好「距今 N 天」，不讓模型自行做日期運算）；財報天數（57 天）被誤當新聞時效（每筆標示「財報｜」或「新聞｜」）；`doc_type` 被填入多值導致查空（非單一合法值一律降級為不過濾）；容器時區為 UTC 使「今天」少一天（三個服務設定 `TZ`）。**已知限制**：LLM 選用 tool 的正確性沒有自動化測試，只能靠每情境三次的端到端手動驗證。

### 二、推理顯示與模型替換評估

**顯示推理過程：功能可行但不納入，開啟推理讓單題延遲增為 6.7 倍。**（本機 `qwen3.5:9b`，真實 MCP + pgvector）

| 設定 | 總耗時 | 答案 | 推理 |
|---|---|---|---|
| 關閉推理（基準） | **186.3s** | 1105 字 | — |
| 全節點開啟 | 660.8s | **0 字** | 3152 字 |
| 僅 `generate` 開啟 | **1245.3s** | 1425 字 | 30891 字 |

答案 0 字是因 Ollama 預設 `num_ctx` 4096，RAG prompt 加上推理內容即超出上限；加大到 16384 可解，但模型不再受限後為一句提問寫了 30891 字推理。壓制推理長度的兩條路徑無效：`reasoning='low'` 與 `True` 推理字數相同，`num_predict` 限制總輸出而推理永遠先於答案，設 600 時答案再被截為 0 字。

**替換模型：`qwen3.5:9b` 是這台 M1／16GB 上唯一可用的模型。** 每情境三次：`4b` 快 25%（140s 對 186s）但資料過期時 0/3 補抓，正是第一節修好的退化；`4b-mlx` 278s，`extract_filters` 結構化輸出 3/3 失敗；`9b-mlx` 逾一小時未完成。「Apple 原生框架應該更快」是合理但錯誤的直覺：失敗源於容量而非框架（embedding 超出 16GB 實體記憶體，swap 一度達 23GB，量到的是磁碟分頁速度），公平比較下 `4b-mlx` 仍比 `4b` 慢一倍。限制來自硬體容量與記憶體頻寬，與架構無關。

結果：`reasoning=False` 維持並在 `src/graph.py` 註記實測數據；`app.py` 過濾 `<think>` 標籤的防護分支永遠不會執行（`generate` 已關推理、`_tool_llm` 輸出不進串流），已移除；UI 新增模型下拉選單，`LLM_MODEL_CHOICES` 只列預設模型，實測不合格的已從 Ollama 移除。

## 2026-09-09　財報數字的靜默錯誤與延遲優化收斂　`資料層` `效能`

承 09-08，換模型與開推理已排除，本次收斂剩下的延遲方向，並處理累積的技術債——其中財報抓取的數字正確性佔了大半，共同特徵是都不報錯。

### 一、延遲優化：三個方向收斂

- **Context 權責分離**：metadata 佔 context 57%（7177 字中的 4064 字），agent 每輪整份重送；改為送進 LLM 的複本只留 `summary_for_llm`。未帶來可量測的延遲改善（瓶頸是生成速度，每秒約 10 字），效益是 context 膨脹速率降低一半以上。
- **資料明顯足夠時跳過 agent 第二輪**：第二輪的唯一產出是模型說「夠了，停」，實測耗時 82 至 106 秒，改為條件路由。與 09-07「決策權交給 LLM」的衝突控制在最小範圍，只收回「資料明顯足夠 → 停止呼叫工具」；誤判代價不對稱（誤判為可結束會拿過期資料作答，誤判回 agent 只多一輪），判準取保守側。總耗時量不出差異，`generate` 的浮動蓋過了省下的時間。
- **決策卡字數約束：實測後不採用。** 同容器、同檢索結果、`temperature=0`，與假設相反：

| 決策卡 prompt | 輸出字數 | 免責聲明 |
|---|---|---|
| 現行（基準） | 924 字 | 保留 |
| 加字數約束 | 1252 字（**+35%**） | **遺漏** |
| 改為限制子條列數量 | 1062 字（+15%） | 保留 |

基準每欄本就 1-2 句、沒有廢話可壓，「含每個子條列」的措辭反而誘導模型展開更多子條列並漏掉免責聲明——長度由欄位規格決定，不由約束決定。

### 二、新聞時效判斷改由 LLM 抽取，與對話持久化

原本關鍵字 regex 只有 90 天與不過濾兩檔，同一條 regex 在兩處各跑一次推出無關的天數，tool 說明又用散文重寫一份。改由 `extract_filters` 一次抽出 `news_since_days`，兩處共用單一來源；夾取 1..365（該值直接進 SQL，回 0 或負數會查成「未來的新聞」而全空）。**取捨**：門檻以 7 天為界而非「有值就收緊」，否則「最近三個月」也會被要求當天新聞。對話歷史持久化的成本在認證而非儲存層（data layer 以 user identifier 分租），續談時仍走 `_trim_for_history` 維持 prompt token 控制。

### 三、財報數字的靜默錯誤

只讓 LLM 讀到看似合理的錯誤數字，比會拋錯的問題更難察覺。

**抓對外國發行人的申報**：這類公司不申報 10-Q/10-K，6-K fallback 卻涵蓋任何重大公告，「取最新一份」偶爾會抓到非財報。改採 `reportDate`（財報的報導期末與申報日不同，公告類填當天）加「月份需為 3/6/9/12」；更嚴重的是 **6-K 的主文件只是封面頁**，本文在同一份申報的 exhibit，ASML 由 2,265 字元變 65k。**已知限制**：`_select_exhibit` 取最大 exhibit 是啟發式，理論上可能挑到投影片；改用類型標籤的升級路徑實測不成立（ASML 樣本中 `EX-99.1` 是新聞稿、`EX-99.2` 才是投影片、真正的財報是 `EX-99.4`），故維持現行啟發式，尚未誤挑過，入庫字數警示是後備防線。

**改為「API 取數字 + 原文取文字」雙軌（台美兩市場）**：兩軌各自入庫、獨立成敗，不可互相取代（API 只有逐欄數字，敘述只在原文，且原文抽文字後表格易錯位）。台股推翻了「MOPS 無官方 API」的前提，爬蟲降級為一軌；API 只收一般業，金融業與興櫃只剩爬蟲。美股走 SEC XBRL，每筆事實帶 `accn`，用它鎖定申報而不必寫會計期間比對。實作期間抓到三個靜默錯誤：概念清單首位已停用（取到八年前的營收）、雙幣別 EPS 的單位鍵是 `USD/shares`（取到台幣值，量級差 30 倍）、時點數字沒有 `start` 而任意挑一期（權益取到兩年前）。另發現 SEC 節流頁是 HTTP 200、`raise_for_status` 攔不住，後備路徑會把警告文字當財報入庫，故加內容長度下限。

**雙掛牌標的先確認市場再查詢**：同一家公司台美都有掛牌時，兩邊數字都對卻不能互比（幣別、期間、每股基準不同；台積電 EPS 實測 49.33 元對 1.36 美元），原本 prompt 要求「台積電→2330」等於替使用者做了選擇。改為只記錄使用者有沒有明講市場：明講了直接查，沒講才反問並附按鈕。不採「一律反問」（已說 TSM 還反問屬多餘）也不採「兩邊都答」（僅詢問台股的使用者也會收到大量美股數字）。雙掛牌 12 檔中 6 檔是 OTC 的 Level 1 或非贊助 ADR，不須向 SEC 申報、連 CIK 都沒有，故只收美股側查得到財報的標的，其餘另立一張表僅供附帶告知。

## 2026-09-13　AI 可觀測性落地與檢索效能實測　`可觀測性` `效能`

同一條線：先讓 AI 行為可計時落檔，才有依據動檢索；平行化與快取以開關讓兩條路徑並存，A/B 實測後推翻了連線池會成為瓶頸的推導。

### 一、從 `print` 改為 logging，AI 行為每日落檔

AI 路徑原有 9 處 `print`，無時間戳、只進 stdout，而 `docker logs` 有輪替上限、容器重啟即失去歷史——**無法回答「上週那一題為什麼跑了 400 秒」**。改用標準庫 `logging` 輸出 JSON Lines 到已掛載的 `data/logs/`，四個 LLM 呼叫點與 `retrieve_context` 各記 `elapsed_ms`，同一題以 `qid`（問題短 hash）串連，`generate` 另記 `prompt_chars`／`answer_chars` 以區分慢在輸入還是輸出。**只記長度不記內容**，避免把提問寫進 log。用標準庫加一個 JSON formatter 即可，不引入 structlog／loguru。

### 二、檢索平行化與 query embedding 快取

`retrieve_context()` 原本依序執行三段檢索，tool loop 重查時又對相同問題重複呼叫 Ollama embedding。改為程序內、有界的 TTL/LRU 快取加三段同時送出的候選預取，行為維持不變。**取捨**：快取讓同一題的重複檢索幾乎免費，代價是 TTL 內對同一字面問題不反映新入庫的資料——以每日批次入庫的頻率可接受。`RETRIEVE_PARALLEL` 開關讓同一個 image、容器、資料上能切換 A/B（六題輪替、每組 7 次取中位數）：

| 組合 | 中位數 |
|---|---|
| 循序 + 無快取 | 236.5 ms |
| 循序 + 有快取 | 24.6 ms |
| 並行 + 無快取 | 202.5 ms |
| 並行 + 有快取 | **11.5 ms** |

貢獻幾乎全來自快取（每次 `embed_query` 都需呼叫一次 Ollama，檢索本身只是幾條 SQL），並行幅度小但離散度較低，兩條路徑回傳的 chunk id 序列完全相同。**連線池 `max_size` 維持 5**：推導上兩個並行檢索就會超額、在 `timeout=2` 後拋 `PoolTimeout`，實測壓到 8、12、20 個並行仍零失敗——每段 `similarity_search` 只持有連線數毫秒，「3 × 並行數」的推估不適用。端到端延遲仍以生成為主，這數十毫秒對體感沒有影響。

**不採用**：Redis 取代程序內 query embedding 快取——單程序架構下跨程序共享收不到額外命中（觸發條件：MCP server 跑多 worker，或快取要跨重啟存活）；單一 SQL 用 `UNION ALL` 取回三段檢索——SQL 條件邏輯難維護，連線佔用本身非問題；改用 async DB driver 取代 `ThreadPoolExecutor`——影響面遠大於收益，並行效益幅度小。

## 2026-09-14　AI 可觀測性延伸　`可觀測性`

同一條可觀測性線的兩段：先把剩下的抓取路徑儀器化並修掉一個讓紀錄失真的判準錯誤，再接上 Langfuse 補足 logfile 答不出的 prompt／token 層級。

### 一、抓取路徑可觀測性修正

剩餘的 `print` 依呼叫端重新分類，50 處中約 39 處其實會在服務請求中執行——是 09-13 儀器化未完成的另一半。更根本的缺陷是 **`fetch_missing_data` 以「沒拋例外」為成功判準，但 fetcher 的失敗多半不拋例外**：查無 CIK、官方 OpenAPI 查無公司、MOPS 版面改版都是正常返回 `FetchResult(False, msg)`，因此 logfile 的「補抓成功」從未為真過。修為接住 `FetchResult` 再取 `.ok`；失敗原因一律用短代碼（`no_cik`／`api_miss`／`mops_blocked` 等），否則無法以 `jq` 彙總。另有兩處是降級而非失敗——`cover_only`（6-K 退回封面頁）與 `no_chinese_doc`（MOPS 改抓替代檔，仍回 `ok=True`），logfile 是唯一能保留這個區別的地方。**已知限制**：只改紀錄的正確性，未改變抓取行為。

### 二、接上自架 Langfuse 與節點層級追蹤

logfile 答得出「哪個節點花了多久」，答不出「送進模型的 prompt 長什麼樣、花了多少 token」。Langfuse 是自架的 LLM 追蹤平台，提問不必送進第三方。掛載點只有一處：`app.py` 的 `_stream_answer` 呼叫 `graph.astream` 時放入官方 SDK 的 callback handler。**追蹤失敗不得影響問答**：進入點全部吞例外，初始化失敗只記一次 warning，未設金鑰即視為關閉。環境限制：Langfuse 只綁 `127.0.0.1`，容器內需改用 `host.docker.internal`；映像內沒有 `.git`，版本號改由 compose 以 `LANGFUSE_RELEASE` 帶入。

**原假設被實測推翻**：原以為 handler 會跟著 graph 往下傳、LLM 呼叫點自動成為同一 trace 的 observation。實際上 handler 記錄的是 LangChain runnable 而非 LangGraph 節點，不呼叫 LLM 的節點（`resolve_market`／`assemble`／`no_result`）根本不會出現；SDK 的 `@observe` 亦不可用（span 在函式回傳當下就結束，之後的寫入落到父層，成為「每個節點 output 都一樣」的成因）。最後由 `build_graph()` 用 `node_span()` 逐一包住九個節點，形成「一次問答一個 trace、每節點一個 span」。**取捨**：節點 input/output 只送摘要，單一節點 span 由 22,485 bytes 降到 605 bytes，代價是 UI 看不到 chunk 全文（要看全文回 logfile）。**驗收**：實跑一次問答，trace 記錄到 input、output、`user_id`／`session_id`，延遲 23,871 ms，token input 21／output 33。**已知限制**：span 樹以 OTel in-memory exporter 驗證，未經 Langfuse UI 目視確認。

另修一個既有缺陷：`python -m src.cli` 自 `build_graph()` 改為 async 後無法啟動（`agent` 節點也是 async，同步 `.invoke()` 會拋 `No synchronous function provided`），`main()` 改 async 並用 `ainvoke()`。

## 2026-09-16　多標的查詢支援　`LangGraph`

**問題**：問「AAPL 和 TSLA 比較」時，抽取器偵測到多間公司會回 `status="error"` 並降級為「不指定公司」檢索。實際追查後問題更嚴重：`status` 全專案只有一行 `log.info` 消費，沒有任何分支或使用者可見訊息，降級後跨全庫檢索會以其他公司的片段組成看似合理的比較答案，使用者無從得知過濾已失效。

**順帶修掉的既有 bug**：`assemble` 原本是最後寫入覆蓋，分次檢索的前幾批 chunks 會被靜默捨棄——雙掛牌「兩邊都要」在此之前一直只拿到一半資料。改為累積並依 chunk `id` 去重。

## 2026-09-17　生成延遲優化：決策卡欄位裁剪　`效能`

「回應延遲過長」在 09-09 被收斂為硬體限制：生成速度穩定在每秒約 10 字，`generate` 單題 90 至 160 秒，輸入側手段已用盡。既然每秒能寫的字數固定，剩下的槓桿就是**要寫的字數**本身。

### 一、病因與設計

**病因是 schema，不是模型。** 決策卡無條件要求 13 個欄位，prompt 卻明文允許其中四欄寫「資料不足」——問「這則新聞對股價的影響」時，系統把最稀缺的輸出 token 花在使用者沒問、語料也不足以支撐的佔位文字上。09-09 字數約束 A/B 失敗（輸出反變長 35%）正是這個結構的症狀：模型同時被要求「簡短」和「填滿 13 欄」，指令衝突時 schema 贏。因此欄位取捨改由應用層純函式 `allowed_fields()` 依使用者意圖與實際檢索結果決定，未入選的欄位**根本不放進 prompt**（保留描述再加一句「請略過 X、Y」，等於先展示再叫模型忽略，與失敗的字數約束同類）。

- **`answer_shape` 不沿用 `doc_type`**：`doc_type` 是資料事實，`answer_shape` 是使用者意圖，兩者常相關但不等價（「這則新聞對股價的影響」是 `news`，卻需要估值欄位）。預設 `"full"`，依據是代價不對稱：誤判成 `full` 只多幾欄，誤判成 `news` 會刪去投資題所需的素材且使用者無從察覺。
- **行情抓取的循環依賴用三態解**：吃行情的欄位要不要納入取決於快照抓沒抓到，但值不值得抓又取決於有沒有欄位要用（`get_market_snapshot` 是 blocking 網路呼叫，冷啟 2.50 至 3.55 秒，擋在 first token 前）。`has_market: bool | None` 的 `None` 表示「還沒抓」、樂觀視同可能有；用 boolean 會自我實現否定。
- **「不得整段棄權」改為測試斷言**：`conclusion`／`facts`／`inference`／`upside`／`risk` 五欄在任何形式、證據狀態下無條件輸出，寫在註解裡會被下一個調 gating 的人破壞，故以形式 × 證據 × 行情的完整交叉組合逐一斷言。
- **取捨**：計時起點前移先獨立 commit，否則舊計時器量不到兩段式行情抓取的節省。`## 📈` 結構邊界改用非 emoji 標記刻意未併入，以免把欄位邊界風險混進效能改動；評估後不採用（解析不依賴 emoji，無穩定性問題），post-check 要擴大到標題層級時再重評。

### 二、驗收

## 2026-09-18　多標的比較題的行情併陳與補抓決策修復　`LangGraph`

兩件獨立工作都由多標的比較題引出：前者補齊行情與比較欄位；後者修掉一條讓補抓決策從未發生的捷徑，並一路修到新鮮度判準、財報時效、補抓對象三層。

### 一、行情逐家併陳與比較欄位

**問題與根因**：`generate` 只抓 `companies[0]` 的行情，其餘標的沒有快照，`allowed_fields(has_market=False)` 因而剔除估值、共識、情境與建議傾向（單一公司 13 欄、多標的只剩 9 欄）。該剔除路徑原為「yfinance 抓取失敗」設計的降級處理；多標的情境下其餘標的並未發起抓取，卻同樣進入此降級流程，等同將「未抓取」誤判為「資料不足」。**修法**：`get_market_snapshots` 並行抓所有標的，`has_market` 改為至少一家成功，部分失敗明講哪些沒有行情；維持單張決策卡、欄內逐家列（每家一張會讓欄名重複 N 次、抵銷 09-17 的裁剪效益），新增多標的專屬的 `comparison` 欄承接對比。跨市場題把美元標成「元」的根因在資料層：`format_snapshot` 從未輸出幣別，故在價格前加 `currency:` 行，而非加文案要求模型從代號推斷幣別（那是在請求幻覺）。

**推翻的假設**：鬆綁 `trend_header`「必須單行條列」無害——A/B 後欄位邊界變糊，已回退。為估值、共識欄各加幣別要求後，模型反而整欄輸出「無法提供估值觀察」（PE 與目標價其實齊備），違反「不得整段棄權」。這是繼 09-09 字數約束後第二次遇到同類問題：**單一欄位的指令密度有上限**。結論：新約束只加在最需要的那一欄；格式契約要靠程式檢查而非文案（即 09-19 的決策卡 post-check）。

**結果**（同容器、`qwen3.5:9b`、`temperature=0`、固定素材）：跨市場（NVDA＋2454）與同市場（2330＋2454）都是 14 欄、有免責聲明、比較表 4 列（3 列定性）、無幣別誤標，消失的 4 欄回來。**已知限制**：兩次跨市場執行幣別一次進表格、一次進小結，格式只靠文案沒有下限保證。

### 二、多標的題的補抓決策從未發生

**現象**：「台積電與ASML」答得空泛、沒有 9 月的 ASML 消息；ASML 新聞距今 65 天，而 Yahoo RSS 當下就有當日新聞——先前判斷「ingest 覆蓋缺口」是錯的，真問題是補抓從未被觸發。**根因**：`route_after_tools`（09-09 的效能捷徑，資料夠新就跳過 agent 第二輪決策，省約 106 秒）取 `min(ages)`，而 `ages` 是多標的與全域市場新聞合併去重的結果，`min` 取到 0 天（來源是順帶補進的全域新聞），路由直接判定結束。**修法**：先補觀測（記實收參數與 `news_ages` 全清單，以區分稀釋、模型不照做、決策未發生三種成因），再縮小捷徑範圍為「多標的一律回 agent」；不在捷徑裡疊第二套規則，因為按公司分組取 `min` 一樣會被 `company` 為 NULL 的全域新聞污染。

| | 修復前 | 修復後 |
|---|---|---|
| 路由 | 跳過 agent（`news_age_days: 0`） | 回 agent |
| `fetch_company_data` | 未呼叫 | 呼叫，`company: ASML` |
| ASML 新聞距今 | 65 天 | 1 天 |
| 總耗時 | 約 199 秒 | 約 370 秒 |

補抓後模型自行重查，證明 09-07「補抓決策交給 LLM」的設計有效，先前只是從未讓它做過這個判斷。**取捨**：多標的題多一輪 agent 加一次補抓（約 170 秒，其中約 105 秒是真實外部請求），省掉的正是唯一能發現「其中一家過期」的機會。**已知限制**：錯過的視窗補不回來——驗收題所問的 2026-09-08 台積電與 ASML 合作新聞已超出 Yahoo RSS 的保留範圍，修復保證「以後不會再漏」。

### 三、新鮮度逐家判斷、財報時效與補抓指名

「多標的一律回 agent」耗時 96～277 秒，補抓重查後模型常只回一句「夠了」。改為逐家各自取自己那次檢索的新聞天數（掃訊息串、按 `company` 分組），任一家過期或未被檢索到才回 agent；實作時一度把各家 `min` 放回 `ages`、下游 `min(ages)` 重現原 bug，被 self-check 的 ASML 65 天案例即時攔下。`has_report` 原本只判存在，舊財報（2454 距今 229 天、NVDA 121 天）會持續阻止重抓；改為最新財報日期在 `_REPORT_FRESH_DAYS=120` 天內，查不到視為過期（門檻為推估值，靠 log 累積後再調）。

守衛叫模型回 agent 後，它仍不執行工具說明裡的比較；把門檻結論寫進 header 能讓它去補抓，卻補錯家（補抓了 header 標為「不需補抓」的 NVDA，真正過期的 2454 從未被補），所以改由程式指名過期標的。第一次實測完全沒生效：`_news_ages_by_company` 對 MCP 回傳的 content block 陣列直接 `json.loads`，`TypeError` 被吞掉——手寫的字串案例繞過了真實線上格式，整套 self-check 也沒攔下。修好後再改為只計最後一次補抓之後的檢索，重複指名由 4 次降為 1 次，2454 新聞由 16 天降為 0 天。

## 2026-09-19　補抓與檢索路徑的待辦收尾　`LangGraph` `RAG`

各自獨立的多件工作，共通脈絡是補抓與檢索這條路徑上累積的待處理項目一併收斂。其中兩件是連帶追出來的：查財報期間維度時發現 JPM 財報全文從未入庫，追出 embedding 整批失敗（第四節）；雙掛牌驗收則暴露財報日標記自始沒成功過（第六節）。

### 一、tool 輪數上限與 `extract_filters` 模型的 A/B：兩項皆維持現狀

輪數上限維持 4：十個樣本的輪數全落在 1 或 3，上限一次都沒被觸及，兩臂其實跑同一條路徑；耗時差也不能算參數效果：A 臂先跑時已更新新聞，JPM／SPCX 那題 487.0s 對 174.0s 的差距即源於此。`extract_filters` 維持 9b：28 題逐欄計分（同容器、`temperature=0`）中，4b 單題中位數 6.6s 比 9b 的 12.7s 快一倍，但關鍵欄 `companies` 25/28 輸給 27/28；`in_scope`、`answer_shape`（範疇外兩題不計，26/26）兩臂皆全對。判斷與觸發條件見「已評估不採用」同名項目。

### 二、補抓期間的進度回饋

補抓中位 67.6s（見第八節），期間進度卻停在「檢索資料庫」。在 `agent` 節點完成、tool 已選定而尚未執行的瞬間，依 tool 名稱（`search_knowledge_base` 不提示）切到「正在抓取，約 1-3 分鐘」；判斷放在 graph 層 `is_fetching`，CLI 同步。**取捨**：只分「有沒有在補抓」，不做逐來源進度——那要改對外 MCP 契約（有外部 client 在用），也會和「補抓改並行」衝突；代價是看不到逐家進度，總耗時也未變。

### 三、財報檢索的期間維度

**問題**：「2330 最新財報重點？」正確的 2026 Q2 排第 242、248 名，`TOP_K=5` 全是 2026-01 的舊 PDF；美股 TSM 的 XBRL 塊寫的是 2024 年報數字，卻排第 1。**根因**：台股是顆粒度不對稱（結構化來源整季壓成 2 塊、PDF 散成上百塊）；美股是 `published_at` 記申報日、stale 的卻是會計期間，同一份申報共用日期，「取最新批次」是空操作。

**修法**：台股給最新一期固定席位併到結果最前面，不動全局排序（調整會影響「比較去年同期」這類問法）；美股改在入庫端逐條濾掉落後期數字，全落後才不入庫。第一版「整份落後就不入庫」被推翻：JPM 與 SPCX 的 EDGAR 全文為 0（事後查明是 embedding 失敗與從未抓取，不是 SEC 沒資料），整份捨棄會使兩家完全沒有財報數字；且 JPM 13 條中只有 2 條落後，全份旗標會把它和 TSM 的 13/13 錯當同一件事。也不靠加文案：chunk 開頭已寫「並非本次申報當期」，LLM 仍照引 2024，格式與正確性契約要靠程式。**結果**：席位排在位置 1-2 且內容正確，舊 PDF 保留在 3-7，「比較去年同期」回歸題仍拿到舊 chunk；落後的 TSM、ASML 塊刪除，JPM 重抓後留 8 條當期數字。

### 四、大型 filing 的 embedding 整批失敗：分批送出

JPM 的 10-Q 切成 1533 塊、一次送入 `embed_documents()`，在 Ollama 端穩定失敗，看起來卻像「SEC 沒有這家的財報全文」。修在全部來源唯一的寫入端 `ingest_text`：分批送出，每批失敗重試一次（連兩次不過就不是暫時性問題）。批次值以實測決定、不取推導值（同一份 1533 塊輸入，每值跑 2 次）：

| 批次 | 結果 | 耗時 |
|---|---|---|
| 100／200／400 | 皆 ok | 192～198s |
| 600 | **FAIL**／ok | 230s（失敗）／267s |
| 不分批（1533） | **FAIL／FAIL** | 335s／344s |

400 是上界且取小沒有代價：呼叫次數從 4 增到 16 總時間不動，成本在 token 總量。失敗時耗時反而更長，符合資源型失敗而非乾淨的門檻拒絕，所以「查表訂上限」從一開始就不對。重試不是形式上的保險：JPM 真實入庫時第 1 批就失敗一次、重試成功。**結果**：JPM 入庫 1533 塊，檢索未退化。`CHUNK_SIZE` 的 A/B 刻意不做——塊變大則塊數下降，分不清是分批修好還是剛好避開失敗區。

### 五、雙掛牌處理：反問繞過與幣別提醒

**問題與根因**：使用者沒講市場卻沒被反問，因為 `resolve_market` 只在 `market is None` 時反問，等於信任模型的一個欄位，而它實測會違反 prompt 自行填值。**修法**：市場判斷移出 LLM，只認問句明寫的市場字樣；「直接打 2330 或 TSM」不算表態（原設計視為已表態，驗收時改判：兩邊幣別、期間、每股基準不同，猜錯代價大於多問一句）。同一家公司的兩個掛牌（`['2303','UMC']`）被抽成兩個標的會被當兩家比，故在抽取源頭收斂；市場已確認時按鈕重跑不再重走流程，省 15.4 秒；`dual_market_warning` 不再寫死幣別，觸發條件放寬為並排代號橫跨台美兩市場（2330 vs NVDA 也該提醒）。**結果**：28 題 `companies` 27/28 → 28/28，全欄 25/28 → 26/28；端到端含市場字樣不反問，裸代號 2330 仍反問。

### 六、決策卡輸出驗證層與兩個順手缺陷

post-check 只寫 log，不擋也不改寫輸出，查欄位集合、免責聲明、引用編號越界、非法引用標記四條。實測模型在中文語境輸出全形【來源N】，而 `_link_citations` 只認半形，整份決策卡一個連結都轉不出來（正式環境已發生但未被察覺），已修。`[即時市場數據]` 現在可被觀測，但模型仍會輸出，故降為低優先、持續觀測；**已知限制**：格式違規仍會送到使用者眼前。另順手修了兩個「後端正常、只在別處可見」的缺陷：`plotly` 未鎖版、重建 image 時解析成 7.0.0，chainlit 前端讀不懂（改鎖 `plotly<6`、`kaleido==0.2.1`）；財報日標記因 `add_vline` 對字串 x 軸求平均而自始沒成功過，改用 `add_shape` 加 `add_annotation`。

### 七、mcp-server healthcheck

**結論：不需要專用 endpoint。** 直接探 `/mcp`，不帶 token 被 Bearer middleware 擋成 401，這正是要的存活訊號（healthcheck 不碰密鑰）；`app` 的 `depends_on` 改為 `service_healthy`，實測約 20 秒由 `starting` 轉 `healthy`。**已知限制**：port 未映射、外部 client（如 Claude Desktop）目前無法連入——Bearer token 已就緒，但只有 `app` 需要連，開 port 只會多一個對外攻擊面。觸發條件：真有外部 client 需求再評估。

### 八、單一公司內的來源補抓改為並行：不做

補抓耗時中位 69% 花在 embedding（n=5，範圍 59-80%），並行只會在同一個 Ollama 前排隊：序列中位 67.6s、並行 53.4s，**實得 14.2s（21%）**。收益不足，而非做法不可行，且已有「約 1-3 分鐘」提示已緩解大部分等待感。跨公司的補抓早已並行，因此只評估單一公司內的來源。觸發條件：使用者反映難等，或 embedding 佔比顯著下降（需新的 n=5）。2026-09-21 補充：logfile 新增 `source` 欄位後，「哪一軌最慢」已可由 log 直接彙總，詳見該日章節第二節。

## 2026-09-20　CHUNK_SIZE 單位量測與切法出處、測試與 log 維護收尾　`RAG` `工程品質`

四件各自獨立的工作：量測 `CHUNK_SIZE` 單位落差並加切法出處（只改切法與量測，不改預設、不重灌）、修兩處測試端隱患、量測後維持 logfile 保留 30 天。

### 一、`CHUNK_SIZE` 單位不一致：釐清落差、加切法出處，預設未動

`CHUNK_SIZE=800` 的單位是字元，但 embedding 消耗的是 token；bge-m3 tokenizer 實測中文 1.60、英文 3.84 字元／token（差 2.4 倍），同樣 800 字元中文約 499 token、英文只有約 208。新增 `CHUNK_UNIT=token` 開關（查不到對應 tokenizer 的模型退回字元計數並記 log），並在 `doc_chunks` 加 `chunk_unit`／`chunk_size`／`embed_model` 三欄、由 `insert_chunks` 統一寫入——這個參數會持久化進共用資料表，不像只影響當下查詢的切臂開關，不記出處，新舊塊混入後就永遠分不出來；既有塊為 NULL，語意即「本欄上線前的舊塊」。**取捨**：不改預設、不重灌全庫（新舊塊相似度不可比；財報來源僅 43 個，優先建的是「按來源重跑 ingest」），代價是候選值（384／600／900）本次只產生量測數字。char 路徑回歸（55 塊 sha256 逐塊一致）、斷網退回字元計數皆通過；token 路徑每塊 ≤ 800 token（max 647）而字元數達 1064。

### 二、測試端兩處修正

`_relax_doc_type` 改為回傳複本：09-19 的保留席位機制讓多條路徑處理同一批 chunk，就地寫入會讓測試 fixture 被永久標記、後續案例靜默失效，改動僅一行，故先行修正。`eval_rag_retrieval.py` 的 E1／E2／E3（新聞時效題）把「距今 N 天」寫死在標注裡，隨補抓寫入就必然失效（E1 期望 57 天、實際 2 天），改為從實際回傳的 chunks 現算；結果 8/13 → **11/13**，B1／B2（無財報情境題）因庫內 21 家公司全有財報、情境觸發不了，改為誠實回報「此情境目前無法測」。

### 三、logfile 保留策略：量測後維持 30 天

log 只記長度與提問雜湊、沒有提問或回應原文，無個資疑慮；`data/logs/` 累積 **1.3 MB／約 8 天**，外推 30 天約 5 MB，校準這個值不會改變任何決策（不像 `_MAX_TOOL_ROUNDS` 會改變系統行為）。**結論：維持 30 天。** 觸發條件：要記錄 prompt／回應全文，或日檔達 GB 等級。

## 2026-09-21　資料覆蓋缺口的查證修復與多輪對話市場一致性　`資料層` `RAG`

主軸是「資料與檢索該有的覆蓋，實際有沒有」：先查證 META 財報全文缺失並補上來源盤點查詢（第一、二節），修復正式環境的多輪對話市場不一致（第三節），補齊零新聞標的（第四節），最後以重數的執行時間與前置查證收斂 golden set、按來源重跑 ingest 等後續規劃（第五至七節），並記下不採用的四項（第八節）與一處觀測計數誤報（第九節）。

### 一、財報資料缺口：META 查證與 `inventory` 盤點查詢

META 在 `doc_chunks` 只有 1 塊 XBRL 數字塊、EDGAR 全文為 0，全庫 14 家美股中只有它的全文軌為零。來源本身完整，**根因是入庫時 embedding 失敗**（`tokenize` 回 400），該軌整份沒入庫；09-10 的低字數防線只攔到 XBRL 那塊，看不到整軌缺席。重跑 `report` 後 EDGAR 全文由 0 補到 740 塊，過程仍觸發「embedding 批次失敗，重試一次」後全數入庫，證實 `EMBED_BATCH_SIZE=400` 的分批與重試機制有效（上線日期不能代替實跑）。

新增唯讀的 `python -m src.update inventory`（`list_sources()`），台股、美股各自判定「全文軌／數字軌」是否為零，ASML、TSM 是外國私人發行人（申報 20-F／6-K），列白名單；市場歸屬走 `is_tw_ticker`，避免兩軌全空的標的被判成不屬於任何市場而漏掉。立刻抓到 **2380 數字軌為零**，補跑後恢復。兩項缺口成因不同：META 是檢查執行了但 embedding 失敗；2380 的 PDF 距今 232 天、超過 120 天門檻，補抓機制本身正確，只是它在查詢當下才評估，若無人查詢就不會觸發評估，覆蓋範圍跟隨查詢流量而非標的清單。兩者事中都看不見，只有全庫盤點問得出，這就是盤點查詢的價值。重建 image 後 21 檔標的全部正常。

### 二、`auto_fetch` 的 log 標籤修正

6514（興櫃，庫內無資料）卻出現 `ok=true`：市場總覽新聞併在同一個迴圈，log 一律掛觸發查詢的公司，資料本身寫對了，但公司別成功率統計虛高。`calls` 改為 `(company, source, fn)`，市場新聞帶 `company=None`、每筆新增 `source=`；不拆獨立節點，避免重蹈行情抓取曾被標成 `node="generate"`、耗時被算進生成節點的錯誤，也不會讓新舊 log 標籤混雜。附帶效果：「哪一軌補抓最慢」可由 log 直接彙總。

### 三、多輪對話市場不一致

**現象**：使用者第一輪問禮來（LLY，美股），追問「美股醫藥有無其他建議投資標的？」，回覆卻整篇是台股內容（來源 cmoney.tw／money.udn.com）。**根因在檢索層，不是 prompt 層**：追問未被改寫、抽不到 company 時早退、`market` 從未參與過濾、決策卡「不得整段棄權」逼模型用撈到的素材填版面；直接餵原問句，`extract_filters` 本就抽出 `market=us`，檢索仍回 4 筆台股／不明文件。只改 `rewrite_question` 的 prompt 反而更糟（`market` 被改成 `both`，`{unknown:4, us:1}` 惡化為 `{unknown:5}`），已 revert。

**修法**：(1) 改寫只在偵測到「上一輪是市場反問」時才附消歧規則；(2) `doc_chunks` 新增 `market`（`tw`／`us`／`NULL`）由寫入端決定，不以代號字面推導（港股 0700、日股 7203 會誤判）；(3) 檢索指定市場時一併排除 `market IS NULL`，放行等於讓認不出市場的新聞繼續填版面；MCP server 是獨立行程，`market` 只能當 tool 參數傳。回填後覆蓋率 10,700／10,865＝98.5%，**`market IS NULL` 殘留 165 筆**：137 筆來自 cmoney（URL 與標題皆無市場線索，需重抓才能修），28 筆來自未納管的 udn／cnyes 版面（可回填，待決定是否納管），寧可留空也不填入推測值。

**結果**：9 題多輪題組 **2/9 → 9/9**；原問題 `{unknown:4, us:1}` → `{us:5}`，「美股半導體最近如何？」混入的台股文件由 3 筆降到 0 筆。`_retrieve_sequential` 無 company 早退時補強不採用：實測皆回滿 5 筆、市場正確，檢索結果為空的前提不成立。

### 四、新聞來源缺口：路由 bug 與台股個股頁來源

4 檔零新聞（TSM、3049、2380、3025），成因分兩種。TSM 是路由 bug：`agent` 節點只取 `_stale_companies()` 的 `stale`、忽略 `missing`，零新聞標的收不到指名補抓的指示；修為兩者都取，`missing` 用「完全沒有檢索到新聞」措辭。另三檔是台股中小型股，Yahoo RSS 不覆蓋：Google News RSS（連結不透明、抽不出內文）、yfinance（與 RSS 同源回 0 篇）、cnyes tag 頁（不同代號抓到相同的無關文章）三個候選實測淘汰，改採 Yahoo 台股個股頁作為 RSS 回 0 篇時的 fallback。**結果**：全庫零新聞標的歸零，三檔各補回 9～10 篇，TSM 補回 16 塊，端到端 log 出現 `missing: ["TSM"]` 並發出補抓。順帶實測推翻「美股標的沒有敘事文件」的前提（NVDA 財報 587 塊），真正的落差在新聞覆蓋不均。

### 五、AI 執行時間重數：瓶頸確認、離群未複現

重數 `data/logs/` 全檔：`generate` 中位 176.2s、佔總耗時 52.6%，`agent` 佔 38.0%，`retrieve_context` 中位 0.5s、佔 0.0%。限定 43 個完整題重算每題內佔比，排序一致（`generate` 平均 59.1%），全檔與單題兩種算法的結論不再矛盾。先前觀測到的 12 輪離群題（2168.9s）未出現第二個同量級樣本，暫不處理。連帶結論：繞過檢索無法降低延遲。

### 六、golden set 是數字直答、chunk 擴充與 `CHUNK_SIZE` 的共同前置

**數字直答通道**：原以為的前置問題「直答的數字沒有 `[來源N]` 編號」不成立——引用編號只依 `doc["source"]` 去重，XBRL／TWSE 數字本就帶完整出處、走同一條入庫路徑。真正的前置是缺少數字題答錯率的量測。**`CHUNK_SIZE`**：重測 384／600／900 三臂，中英文 token 分佈都已對齊，但量的是分佈而非檢索品質，無法據此選值；現行參數沒壞（8,185 塊財報與 2,680 塊新聞無一超過 1000 字元，最壞 687 token 對 8192 context 差約 12 倍）。**結論：機制已備、選值依據未建立**，觸發條件為 golden set 到位而能量出檢索品質差異，或正式環境出現實際截斷。

**golden set 規格**（三項共用）：50-100 題，涵蓋單一數值、年增率計算、跨年度比較、表格問答、註腳問答、管理層歸因、風險因素、同詞多章節歧義八類，量 Recall@5／@10、context precision、citation 正確率、表格數值正確率、token 成本與延遲，沿用 `tests/eval_data/*_annotations.json` 加 checker 腳本的模式。chunk 擴充的 parent-child 受限於 `pypdf.extract_text()` 拿不到標題層級（要換 parser 並改 schema），表格獨立處理的收益只落在約 11% 的中文語料（938／8,185 塊）；數字直答只剩消除檢索誤差一項價值。

### 七、按來源重跑 ingest 的能力盤點（規劃，尚未實作）

查得出缺口之後，如何讓某來源重新抓取入庫。三個場景共用這項能力：chunk 參數改變、embedding 模型換代（向量維度綁死 bge-m3 的 1024 維，必須全庫重來）、來源內容更新（META 的缺口即由人工查出）。`source` 欄位有四種前綴：`EDGAR`／`SEC-XBRL`／`TWSE-API` 可依前綴分派回既有 `fetch_*`；新聞不需重跑（90 天內佔 98%、自然汰換）；`data/*.pdf` 是本地路徑，只能在檔案還在時重讀——9 個目前都在，但此屬偶然而非設計保證。重跑必須是「查出 source → 分派 fetch → 走 `ingest_text`」整條，落點在 `update.py`；`delete_by_source` 已負責去重。尚缺：批次分派與失敗隔離（單一來源失敗不中斷整批）、PDF 檔案不在時明確失敗並記 log、重跑前後塊數對照，以及 `EMBED_BATCH_SIZE` 重驗（400 是依現行塊數實測，塊變大不可沿用）。**效益評估**：只有「來源內容更新」是現在就有的需求，最小可用部分是三種可重抓前綴的分派重跑，不建議一次做完整套；單一標的現可手動 `python -m src.update report --market us|tw --company X` 重抓。

### 八、判斷不採用的四項

- **跨來源標題相似度去重**：Yahoo 台股個股頁與 Yahoo RSS 覆蓋面互斥，重複率預期極低，相似度門檻需實測但庫內沒有樣本可量。觸發條件：出現實際跨來源重複樣本，或新增第三個台股新聞來源。
- **新聞定時排程**：維持查詢驅動。專案非常駐運行；補抓 69% 花在 embedding，背景排程會與前台查詢競用同一個 Ollama（單題延遲已 186-470 秒）；定時抓取會為無人查詢的標的付出 embedding 成本。觸發條件：改為常駐服務或部署正式環境持續運行。
- **補抓軌別拆成獨立 MCP tool**：拆分早已完成（`calls` 各軌獨立成敗，「查 RAG」與「補抓」已是兩個 tool），進一步拆分無法降低主要成本，程式依庫內狀態裁剪比讓 LLM 猜準，還可能多花輪數。觸發條件：log 量到不必要軌別的浪費佔比。
- **雙掛牌對照表改為 API 查詢＋落地快取**：對照表實際有 12 檔（主表 6 檔、OTC 6 檔）且帶業務判定——ADR 端點答得出「有沒有 ADR」，答不出「美股側查不查得到財報」，API 化只解掉一半；新增是數年一次、成本是往 dict 加一行。觸發條件：檔數成長到人工維護吃力，或找到同時回答兩者的端點。

### 九、`[即時市場數據]` 觀測計數的誤報修復

09-19 把「模型自創 `[即時市場數據]` 引用標記」降級為可觀測（`unknown_citation_marker` 只記 log）。累積 17 筆命中中 **13 筆是誤報**——命中的是 `已知事實`、`推論` 兩個欄名，模型照 prompt 要求寫出 `【推論】`，驗證層卻把它記成違規。掃描時整組排除預期欄名後，真正的 `[即時市場數據]` 剩 7 筆。**本項狀態不變**：仍是既有行為、低優先、繼續觀測；這次修的是計數被假警報污染，並量出了誤報率（13/17）。

## 2026-09-23　靜態檢查導入、既有缺陷修復與測試套件遷移至 pytest　`工程品質`

主軸是導入 Ruff 靜態檢查，並處理過程暴露的既有問題：MCP server 的無驗證啟動風險、CLI 路徑上完全失效的 logging；另有兩個獨立發現的 bug；最後把測試套件遷移到 pytest。

### 一、Ruff 規則集校準

預設規則得 3,711 筆告警，**規則集選擇才是主要工作**：中文全角標點的 ambiguous-unicode 三條與 E501 行寬（專案原無慣例）直接排除，tests/ 與 CLI 進入點的 assert／print 以 per-file-ignores 放行，結果降至 48 筆。DTZ 的 11 筆判定不可修改：部署層固定 `TZ=Asia/Taipei`，且 `vectorstore.py` 要對齊 Chainlit 寫入的 naive 本地時間字串，改 UTC 會讓「今天」在台北早上 8 點前退回前一天。isort 刻意不納入，避免 `--fix` 製造與功能無關的大 diff。

### 二、安全面：金鑰洩漏查證與 MCP fail-closed

**Ruff 安全告警**：四筆逐筆判定——S608（SQL 值皆參數化）、S324（sha1 僅作 log 關聯鍵）為誤報，S314（解析 Yahoo RSS，非使用者輸入）低風險，S104（容器內需綁 `0.0.0.0`）背後的真問題是無 token 仍啟動，即下述 fail-closed。**金鑰**：查證 git 歷史（146 個 commit）未發現洩漏——`.env` 從未被追蹤，`.gitignore` 在初始 commit 就含 `.env`。**已知限制**：這是「未發現」而非「已證明無洩漏」，貼進 issue、PR、聊天的金鑰查不到。**MCP**：`MCP_AUTH_TOKEN` 缺失時原本只印 warning 就以 `0.0.0.0` 啟動，等於可能暴露無驗證的公開 tool 端點。**取捨**：只在容器內缺 token 時拒絕啟動（exit code 1），本機維持 warning 放行——目前沒有第三方外接 client，嚴格版擋不到真實風險、只讓本機開發多一道手續。重建 image 後實跑，三種情境行為皆符合預期。

### 三、CLI 進入點的 logging 缺口

原計畫只把 `update.py` 一行 `print` 改成 `log.info`，改完卻發現 `data/logs/` 當天沒有對應檔案：`setup_logging()` 只在 `app.py` 與 `mcp_server.py` 被呼叫，`update.py` 的 `main()` 從未呼叫，其與 ingest 的所有紀錄一直只落到 stderr，讓可觀測性目標在抓取這段實際失效，終端卻看不出來。在 `main()` 開頭補 `setup_logging("update")` 一行，順帶救回 ingest 的耗時紀錄。

### 四、補資料迴圈退化與新聞失敗回報矛盾

## 2026-10-07　雙掛牌比較的數字可比性與 Ollama context 截斷　`資料層` `LangGraph`

同一條調查線：雙掛牌比較題讓模型自己換算幣別與股數比，不是算錯就是拒答，改為程式先算好、模型只引用。A/B 驗證時發現答案常在固定字數斷句，查出是 Ollama 的 context 過小造成 prompt 被靜默截斷。之後修的是同一類問題的另一面：資料餵給模型時缺了單位或期間，模型只好自行推測，把不可比的數字當成可比。

### 一、ADR 溢價與 EPS 換算改由程式計算

模型只拿到兩個幣別的報價，沒有換股比例與匯率，自己換算會與報價矛盾，問 EPS 差多少不是拒答就是算錯（比例乘反、把台幣當美元）。改為程式內算好：`ADR_RATIO`（對照 FY2025 20-F 核實）× `USD/TWD`，兩邊報價都成功才附溢價區塊；兩邊最新 EPS 公布日相差 3 天內視為同季，才附 EPS 換算值。`ADR_PREMIUM` 開關供 A/B：引用溢價率 3/3 對 0/3；EPS 引用換算值 3/3 對 0/3（無換算臂兩次算錯、一次拒答）。

### 二、Ollama context 截斷

Ollama 以 4096 context 載入 `qwen3.5:9b`，超長 prompt 被靜默截到約 2050 token，模型看不到被截掉的輸入卻不報錯。三節點改為記錄 Ollama 回報的 token 用量與耗時，並新增 `OLLAMA_NUM_CTX` 讓三個 `ChatOllama` 共用（`num_ctx` 不一致會讓 Ollama 重新載入模型）。四題 × 三組：

| `num_ctx` | 截斷 | 決策卡欄位 | `[來源N]` 引用 |
|---|---|---|---|
| 4096 | 4/4 題皆截到 2050 token | 0～1 欄 | 0/4 |
| 16384 | 0/4 | 9 欄 | 4/4 |
| 32768 | 0/4 | 9 欄 | 4/4 |

**結論：預設 32768。** 品質與 16384 相同，但歷史最長 prompt 達 22048 token，16384 裝不下。**取捨**：多付約 0.7 GB 記憶體；ADR 比較題 11338 token 的 prompt 光讀約 130 秒、總耗時 306 秒，縮 prompt 評估後不做（見「已評估不採用」）。**已知限制**：Ollama 回報的是截斷後的 token 數，程式端只能偵測「貼著已知截斷上限」，剛好落在該範圍但未截斷時仍會誤報。

### 三、數字可比性：跨幣別、跨期與累計 EPS 誤讀

**問題**：驗收時模型直接比台股 27.25 元與 ADR 4.31 美元，說「台股 EPS 較高」（換算後約 27.4 元，其實 ADR 較高）。**根因**是兩份指示衝突（`dual_market_warning` 要求「不得換算比較」，區塊卻已算好等值），加上資料缺單位或期間。**修法**：有換算區塊時改用 `dual_market_warning_adr`，要求引用等值與差距；換算區塊只在同季時給 EPS 等值並解釋差距；共識營收標「億」與幣別（TSM 預估以 TWD 計價，原值被讀小 10 倍）；季別明寫（`Q2 2026 results (quarter ended 2026-06-30)`，**取捨**：假設曆年制會計年度，日後納入非曆年制公司要改推算）；EDGAR 6-K 切段遺失欄名、49.33 曾被當成 ADR 美元 EPS，改為來源標頭加註幣別與口徑警語。

**台股累計 EPS**：TWSE OpenAPI 的綜合損益表是年初至當季累計，Q2 的 49.33 是 1～6 月累計，單季為 27.25，模型曾拿 49.33 去比 ADR 單季等值。標題、EPS 行、TWSE-API 來源與即時市場區塊四處補標示，並對 2308、2379、2380、2454、3008、3025、3049 七家重抓。驗證（`qwen3.5:9b`，每題 1 次）：同季題 EPS 換算 27.45 對 27.25（+0.74%），不同季題標累計並判定不可比；pytest 283 passed、4 skipped。**「不同季」情境未改用單季 EPS，結案不修**：情境罕見（2330 與 TSM 的 Q1、Q2 都同日公布，「不同季」是驗證腳本寫死的假資料）、有害行為已消除、兩種 prompt 補強都失敗已還原，且證交所 OpenAPI 只給最新一季快照、無法自行算出單季值。

### 四、個股題混入無關公司內容

EPS 題的答案混入不相關的 Penguin Solutions 財測，**根因**是檢索時把 company 為空的市場新聞補進個股題，帶其他公司代號的文件也會混入。移除市場新聞補位，`assemble` 在題目有指定公司時只保留指定公司與 peer 的結果；量測腳本 6 次皆無 Penguin 內容。
